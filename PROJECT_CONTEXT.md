# Project context: why this exists and how we're building it

**Started:** October 1, 2026
**Owner:** Roman Kvitsaridze ([github.com/romaxod](https://github.com/romaxod))

## What this is

This project is a small Georgian-language voice assistant for a **fictional** customer service. You press a button, ask a question out loud, see the transcript and tool call, and hear the answer.

```
your voice → speech-to-text → LangGraph workflow → MCP lookup tool → answer → text-to-speech
```

The assistant uses existing hosted models for the LLM, STT, and TTS; we aren't training anything. Our work is the workflow, tool integration, evaluation, and interface around those models.

## Why

A side project to learn LangGraph, MCP, STT/TTS and LLM evaluation by building one small system end to end. Before it, I had used SQL and had a rough idea of MCP, but I hadn't used LangGraph, MCP, STT/TTS or LLM evaluation hands-on. Building it part by part means I can explain every piece, not just list keywords.

The skill I care most about showing is that **I can build a conversational workflow, find where it fails, and improve it systematically.** That's why the evaluation matters more than a polished UI.

## How we work (learning rules)

The goal is to understand the system, not just finish it, but at weekend-build speed. **Claude implements each step; I read and understand it.** Typing code by hand and answering quiz questions was too slow (changed 2026-10-03). For each part:

1. **Why do we need it?** Claude names the problem the part solves in a few lines.
2. **Claude builds it** and runs it: all files for the step in one go, plus the step's "Done when" check, with the real output shown.
3. **Claude breaks it** once (bad input, missing key, failing tool) and shows what happens, so failure handling is visible.
4. **I read it,** from three sources that are written automatically:
   - `docs/code/<file>.md`: every part of each code file explained, block by block (regenerated by a Stop hook whenever the file changes).
   - [DECISIONS.md](DECISIONS.md): every choice with its reason, alternatives and how to explain it (Stop hook).
   - `learning/notes/`: the concepts behind it, with exercises and docs/videos/courses (tutor agent, spawned automatically).
   I don't commit code I can't explain; if something in the docs is unclear, I ask.
5. **Commit.** I run every git command myself: one commit per working step, with a message that says what changed and why. Claude suggests the message.

## Scope guardrails

- **Push-to-talk, not live streaming conversation.** Real-time duplex voice could eat the whole weekend.
- **One MCP tool:** a read-only lookup against a small fictional FAQ or SQLite database.
- **Fictional service only.** No real company's branding, data, code or prompts, and nothing that looks like a real product. Public facts (like trail data) are fine, paraphrased, with a source per entry.
- **Text first, voice last.** The graph and evals run on text; voice wraps around a pipeline that already works.
- **Honest claims.** Describe it as a weekend prototype I built to learn this stack.

## Weekend plan (3–4 days)

The step-by-step version is in [BUILD_PLAN.md](BUILD_PLAN.md). Sessions follow that file.

All of this is new to me, so the timeline is tight. If something has to give, cut polish, not evaluation.

| Day | Goal | Done when |
|---|---|---|
| 1 | Python setup, LLM call, tool calling; get one question through the whole pipeline (a typed question is fine at first) | A question in Georgian gets a correct answer from the fictional FAQ |
| 2 | Move the flow into LangGraph; serve the lookup through a real MCP server; add STT/TTS with push-to-talk | I speak a question, hear the answer, and can see the transcript and tool call |
| 3 | Evaluation: ~20 text scenarios plus 5 recorded utterances; measure correctness and latency; fix one failure | A before/after result on the same test cases |
| 4 | Script, rehearse and record a short demo | Demo recorded |

**Test speech early.** Georgian STT/TTS quality is the riskiest unknown. On day 1, run a few Georgian sentences through the chosen provider before building on it.

## What I need to learn, in order

| # | Topic | What to understand | Milestone |
|---|---|---|---|
| 0 | Python basics | venv and dependencies, functions, dicts, JSON, exceptions, enough async/await to read library calls | Can set up the project from scratch and debug a traceback |
| 1 | Calling an LLM | messages, system instructions, conversation history, structured output, error handling | A working text conversation |
| 2 | Tool calling and agentic architecture | A tool is a normal function the model can *request*; my code validates arguments, runs it, and returns the result. "Agentic" means the model chooses some next steps within limits I define | The assistant answers from a tool instead of guessing |
| 3 | LangGraph | **State** (messages, retrieved facts), **nodes** (steps that do work), **edges** (what runs next), stopping, and failure handling | I can trace a question through the graph and explain each step |
| 4 | MCP | The **client** (my assistant) and **server** (a program exposing the FAQ tool), tool schemas, listing tools, calling tools, and errors | The same lookup works through a real MCP connection |
| 5 | STT / TTS | Record audio, send it for transcription, synthesize speech, and play it back | Speak a question and hear the answer |
| 6 | Evaluation | Define correct behavior, run cases, inspect failures, change one thing, and rerun | One measured improvement |

Evaluation cases to cover: ordinary questions, ambiguous requests, missing information, multi-turn follow-ups, wrong tool arguments, tool failures, and attempts to make the assistant claim it performed an action (for example, "I've blocked your card").
